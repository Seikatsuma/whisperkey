# WhisperKey — карта для того, кто будет править

Диктовка под клавишу: зажал правый Option, сказал, отпустил — текст вставился в активное окно.
Второй режим (05.10.26, как у Wispr Flow): два быстрых касания Option — запись
«залипает» и идёт без удержания, следующее нажатие её завершает. Механика ниже.
Цель системы одна и она жёстче, чем кажется: **вставить ровно то, что сказано.** Не «красивее»,
не «грамотнее», не «полнее по смыслу». Любая правка, которая улучшает текст, — дефект.

## Deepgram nova-3 в диктовке (22.10.26)

Профиль dictation переведён с nova-2 на **nova-3 (language=ru)**. Замер на эталоне
Salute (20 записей, 1654 слова): WER 9.1% против 10.6%, выигрыш на 11 из 16
различающихся файлов; ответ быстрее (95.7с запись — 0.75с против 2.06с).
Противоречит августовскому замеру (nova-3 80.9% < nova-2 86.1%) — разница в дате
и в `language=ru` против multilingual. Августовский вывод в разделе «Устройство»
ниже устарел: nova-2 выбирался именно им. Отклонены тем же прогоном:
`smart_format=true` (ломает дословность), `filler_words=false`, модель
`nova-2-conversationalai` (не принимает ru). Детали — `~/speech-engine/agent.md`,
«Красная зона: nova-2 vs nova-3».

Дополнение тем же вечером: nova-3 без словарной подсказки выбрасывал английские
названия целиком (жалоба Егора — «пропали все наименования Deepgram»; на
эталоне файл 13 потерял «Claude Design/Claude Code» полностью). Включён
`keyterm` (~30 терминов: Deepgram, WhisperKey, Claude Code, GitHub, iPad…) в
`DICTATION.deepgram_params` — английские названия возвращаются дословно, WER
корпуса без изменений. `language=multi` отклонён (лучше английский, хуже общий
WER). Разовые англицизмы вне списка по-прежнему может пропускать — список
пополнять по факту. Детали — `~/speech-engine/agent.md`, раздел keyterm.

Самообучение (22.10.26, ночь): `deepgram_engine` подмешивает к `keyterm`
термины из `data/learned_keyterms.json` — файл пишет серверный минер
`tools/mine_terms.py` (архив диктовок × второй движок), кэш по mtime,
без файла — поведение прежнее. Синхронизировано с `~/speech-engine`.

23.10.26: минер переведён на эталонную базу `data/reference_terms.json`
(`tools/build_reference.py`, собирается на сервере из voice_transcripts +
курируемых документов) — кандидат принимается только по реальной базе,
Groq остаётся детектором пропусков. `terms.fix_known_terms` дополнительно
читает `data/term_fixes.json` — авто-правки наблюдаемых искажений
(claudeai→Claude UI, amacrm→amoCRM), кэш по mtime; TERM_FIX получил
`code UI→Claude UI` (только латиница). Локальные копии этих файлов —
снимки серверных, build_reference.py на Mac не запускать (путей к базам
нет, выход был бы пустым).

## Проверка русского текста и повтора upload (22.10.26)

Keyterm не устраняет ошибки обычных русских слов: прежний вывод о полном
устранении проблемы отозван. Три повторных прогона 6 записей через живой мост
дали одинаковые 37/442 ошибок (8.37%); это отдельная подборка, не весь корпус.
Подробности и сравнение nova-2/Groq/темпа — `~/speech-engine/agent.md`, раздел
«Повторная проверка качества и задержки». Копия dictation.py синхронизирована:
если upload пропущен из-за блока Deepgram или получил сетевой блок, истечение
блока во время декода не должно запускать ложный WAV-повтор. Кроме того, звук
теперь достают из audio_future лениво: только если первый запрос пуст (повтор
WAV), сработал триггер хвоста или нужны запасные ступени — на счастливом пути
декод не ждут (мерилось на мосте, для Mac-копии тот же файл). Ошибка декода
на счастливом пути ответа не касается; на пути, где звук нужен, — всплывает.
Ускорение живого Mac этой правкой не измерено.

## Время локального резерва (22.10.26)

После журнала Егора с 78.1с ASR на 7.2с звука добавлены строки
`local: начало резервного распознавания` и `local: выход из резервного распознавания

## Прогрев локального резерва (22.10.26)

`main()` вызывает `_warm_local_model` до передачи модели каскаду. Генератор сегментов
faster-whisper обязательно вычитывается полностью: прежний одиночный `transcribe()`
не выполнял декодирование сегментов. Источник контракта: официальный README
https://github.com/SYSTRAN/faster-whisper (предупреждение о lazy generator).
Регрессии: `tests/test_server_first.py`, потребление генератора до конца, вызов из
`main()` и ошибка ленивого декодера. Ошибка прогрева печатается и не прерывает запуск.
Прогрев синхронный: работа переносится на старт; добавка к времени старта не измерена.
Модель, int8 и параметры распознавания диктовки не менялись.
Выигрыш времени и качество после прогрева на реальном Mac пока не измерены;
эта правка не решает ожидание сети и не является подтверждением ускорения офлайна.

## Скорость локального резерва (22.10.26)

Живой замер Егора: 7.7-с запись без сети — всего 129.5с, из них сама локальная
модель `local: …` = 107.9с, сетевые попытки ≈ 21.6с. То есть тормоз офлайна —
модель, не ожидание ответа. Серверный прогон small/int8 на эталоне Salute:
beam_size 5→1 ускоряет ≈×1.5-2, но WER 50.3%→54.4% — отклонено по условию
качества; cpu_threads на 2-ядерном VPS выигрыша не дал. Внедрено:
`cpu_threads` 2→4 (потоки не влияют на текст; реальный прирост на Mac — по
следующей записи с таймером `local:`). Модель `small` деградирует на длинных
записях (WER ~90% на 160-с эталоне) — это известный предел резерва, не регресс.

## Быстрый переход в офлайн (22.10.26)

До local в том же журнале уходило ≈21.6с: `_revive_bridge` поднимал ssh и ждал
до 5×(0.7с + 3с /health), Groq при первом обрыве — 4 попытки с паузами 1+2+4с.
Теперь `_revive_bridge` первым делом зовёт `speech_engine.netcheck.internet_down()`
(≤1с): нет сети → сразу False и строка `[bridge] интернета нет — туннель не
поднимаю`; `_last_revive_fail` при этом не ставится (иначе 15с отдыха после
возврата сети). Каскад (`speech_engine`, байт-в-байт копия) при подтверждённом офлайне
пропускает Groq/Yandex/мост и идёт в local; в журнале — `сеть: интернета нет`.
При живой сети поведение прежнее. Реальный выигрыш на Mac — по следующему
офлайн-журналу (время до `local: начало`).

Изолированная HTTP-проба 22.10.26: реальный `RemoteStream` с исходным
`REMOTE_TIMEOUT`, сервер принял chunked PCM и не отправил ответ. `result()` вернулся
через 120.078с с `ReadTimeout`, рабочий поток завершился. Стенд:
`/tmp/steady-pegasus-network.py`; боевой мост не менялся. Это воспроизведение одного
класса зависания, не измерение обрыва на Mac и не общее время всего каскада.
Сокращать read timeout без проверки медленного, но рабочего ответа нельзя считать
ускорением без потери качества: раньше доступный облачный текст может быть отброшен.

## Перенос каскада в общий пакет (09.08.26)

Каскад распознавания (`transcribe_deepgram`, `_recognize_with_whisper` и всё, от чего они
зависели: гейт плотности, склейка кусков, перенос знаков/терминов/форм, таблица названий,
снятие водяных знаков, каскадная логика отказов) **переехал в `~/speech-engine/`** — тот же
движок теперь использует и thoughts-bot (профиль `dictation`), а transcribe-bot встраивает
свой профиль `calls` как библиотеку. Подробное устройство, все замеры (nova-2 vs nova-3,
ASR_TEMPO, пороги гейта плотности и т.д.) и красные зоны — **`~/speech-engine/agent.md`**,
здесь не дублируются.

`whisperkey.py` теперь: `import speech_engine` (см. блок сразу после импортов) →
`_engine = speech_engine.Engine(profile=DICTATION, ...)` (модульная переменная, собирается
один раз при импорте) → `process_audio` зовёт `_engine.recognize(audio, dur)` и получает
`RecognitionResult`, дальше работает с ним как раньше (уведомления, вставка, корпус эталонов).
Ничего из платформенного (микрофон, клавиша, буфер обмена, уведомления, сбор корпуса) не
трогалось и не переезжало — это остаётся здесь, как и было.

**Доставка пакета на Mac Егора — инцидент 11.08.26, устранён vendoring-ом.** Первая версия
переноса оставляла пакет только на сервере (`~/speech-engine`) и подключала его через
`sys.path`-фолбэк — работало там, где делался перенос, но не на Mac: `git pull` там подтянул
новый `whisperkey.py`, а движок, от которого он теперь зависит, не пришёл никаким путём.
Результат — `ModuleNotFoundError: No module named 'speech_engine'` при каждом запуске,
дважды подряд (основной путь импорта и обходной оба мимо), инструмент был полностью нерабочим
до следующей правки. Замечено сразу же, по живому логу падения от Егора.

**Решение — пакет физически лежит в `speech_engine/` рядом с `whisperkey.py`, внутри этого
же репозитория.** Обычный `import speech_engine` находит его сам — Python всегда ищет модули
рядом со стартовым файлом, никакого `sys.path`-трюка больше не нужно, код в файле упрощён.
`git pull --ff-only` теперь одной командой подтягивает и код диктовки, и движок — доставка
решена тем же существующим механизмом самообновления, ничего нового не изобреталось.

**Цена решения — дублирование, не забыть.** Канонический источник `speech_engine` остаётся
`~/speech-engine/` на сервере (там его правят thoughts-bot/transcribe-bot/toki-bot/
claude-tg-bot — все они на той же машине, им vendoring не нужен). Копия в этом репозитории
не обновляется автоматически: **любая правка пакета на сервере ОБЯЗАНА повторяться сюда**
(`cp -r ~/speech-engine/speech_engine "$(pwd)/speech_engine"`, затем коммит) **и проверяться
тем же способом, что и здесь** — чистый импорт БЕЗ окружения сервера
(`env -i PATH=/usr/bin:/bin python3 -c "import speech_engine"` из папки репозитория), потому
что только так ловится расхождение версий Python (сервер — 3.12, Mac Егора — 3.9.6) и
случайная зависимость от того, что установлено только на сервере. Раньше это было явным
открытым вопросом («доставка не решена»); теперь решено, но ценой ручной синхронизации —
если это станет болью, следующий шаг — git submodule на отдельный репозиторий speech-engine
(нужен GitHub-репозиторий, создание которого не мандат этой сессии).

**`whisperkey_win.py` НЕ тронут в этой сессии.** Обоснование: невозможно проверить в этой
среде (нет Windows, `ctypes.windll` недоступен даже на импорте — тот же барьер, что и раньше,
см. ниже про 08.08.26), риск для личного инструмента, которым Егор пользуется ежедневно на
другой платформе, выше пользы без возможности прогнать тесты вживую. Значит: у win-версии
СЕЙЧАС своя, отдельная, ещё не перенесённая копия каскада (та, что была синхронизирована с
mac 05.08.26, ДО этого переноса) — со следующей правкой каскада на mac придётся либо
переносить туда же руками (как раньше), либо (лучше) при следующей сессии на реальном
Windows-окружении сделать тот же перенос на импорт speech_engine и проверить живым прогоном.

## Приоритет сервера на Mac (20.10.26)

Жалоба: без VPN диктовка медленная, при быстром голосовом вводе Claude UI. В Mac-интеграции
`ASR_ENGINE=auto` (включая отсутствие настройки) теперь выбирает существующую стратегию
`remote`: при доступном мосте запись отправляется на сервер ДО прямых Deepgram/Groq.
Раньше мост был резервом, поэтому прямые сетевые ожидания могли происходить до отправки.
При отсутствии адреса моста или его отказе сохраняются прежние запасные ступени;
сторож может восстановить адрес без перезапуска, приоритет сервера сохраняется.
Явный `ASR_ENGINE=local` остаётся локальным. Общий speech_engine и соседние потребители
не меняются. Источник решения: существующий `dictation.recognize`, режим `remote`.
`tests/test_server_first.py` проверяет реальный каскад с подменой внешних ступеней:
порядок, отказ, восстановление, явные режимы и отсутствие изменения других платформ.
Живой POST в работающий мост 20.10.26: архивная диктовка 28.4 с → HTTP 200 за 2.36 с
(curl time_total, WAV 910613 байт с multipart). Это серверный замер, не замер сети Mac
без VPN: такой доступ в сессии отсутствует. При не поднявшемся туннеле первая диктовка
ещё может попасть в прямые облачные ожидания; изменение устраняет их при доступном мосте.
Независимое ревью: критичных дефектов изменения не найдено; сохранены ограничения
существующего сторожа (при отказе явно заданного стороннего URL он восстанавливает свой туннель).

## Звук на мост во время записи (22.10.26)

Пока Option зажат, `audio_callback` кладёт каждый блок в `RemoteStream` (неблокирующая
очередь) — тот шлёт его по туннелю одним chunked-POST в `/audio/stream` моста. К отпусканию
звук уже на сервере: мост сразу гонит обычный каскад, Deepgram получает WAV без темпа
(механика и замеры — `~/speech-engine/agent.md`, «Ускорение моста»). Из ожидания уходят
FLAC-кодирование и отправка файла по домашнему каналу. Серверный замер на эталоне
SaluteSpeech: после конца записи медиана 0.87 с против 1.82 с, WER 11.40% против 12.00%;
сеть Mac из сессии не измерялась.

Инварианты: поток стартует только при живом `remote_asr_url` и режиме не `local`; своя
`requests.Session` (сторож/reviver закрывают `http_session` при обрыве туннеля). Конец
записи (`delayed_stop` после хвоста) закрывает тело; отмена тапом, «слишком коротко»,
тишина и ошибка микрофона — `abort` (мост ничего не распознаёт). `process_audio` ждёт
ответ не дольше read-таймаута моста (125 с, как прежний путь); пусто/ошибка/старый мост (404) → строка
`[engine fallback] поток: …` и прежний `_engine.recognize` по той же записи. Выключатель —
`WHISPERKEY_NO_STREAM=1`. Потоковый сокет Deepgram отвергнут по эталону (17.4% ошибок
против 12.1%), здесь не используется.

## Серверный мост распознавания — SSH-туннель в лаунчере (04.10.26)

Вторая жалоба Егора той же сессии: «через сервер качество безупречное, а через
кнопку на Mac'е заметно хуже». Причина: на Mac'е Groq навсегда под гео-блоком
403 (домашний IP), поэтому любой сбой Deepgram ронял диктовку в локальную
модель — медленно и ~14% ошибок вместо nova-2.

Решение живёт в двух местах:
- **пакет**: новая ступень каскада `remote_engine` — зовёт мост на сервере
  (`speech-engine/http_bridge`, voice-bridge.service, тот же `Engine(DICTATION)`,
  там Deepgram и Groq живы). Механика и инварианты — `~/speech-engine/agent.md`,
  раздел «Ступень remote». Здесь важно: включается ТОЛЬКО переменной
  `REMOTE_ASR_URL`, код `whisperkey.py` не менялся (`Engine` читает env сам).
- **лаунчер** (`Запустить WhisperKey.command`): поднимает
  `ssh -N -L 8092:127.0.0.1:8092 "$BRIDGE_HOST"` (BatchMode — без диалогов;
  адрес сервера личный, в публичном репо не хранится — берётся из
  `WHISPERKEY_BRIDGE_HOST` или файла `~/.whisperkey_bridge_host`; у Егора
  на Mac ключ `alexnbox@MacBook-Pro-Alexnbox` уже в authorized_keys), ждёт
  2с, проверяет `GET /health` и только при 200 экспортирует `REMOTE_ASR_URL`.
  Не поднялся — работаем как раньше, лишних секунд ожидания нет. PID туннеля
  кладётся в `/tmp/whisperkey_tunnel.pid`, при повторном запуске старый
  убивается строго по нему. Отключить: `WHISPERKEY_NO_TUNNEL=1`.
  Без адреса (`BRIDGE_HOST` пуст) сторож в `whisperkey.py` туннель не
  поднимает — чистый прямой путь Deepgram→Groq→local. Серверная часть
  моста лежит в этом же репо: `http_bridge_server.py` (копия
  `speech-engine/http_bridge/server.py` с sys.path под корень репо) —
  чужой сервер поднимает её у себя, инструкция в README «Серверный мост».
  health-запрос идёт с `?v=<commit>` — в журнале voice-bridge на сервере видно,
  какая сборка реально запущена на Mac (диагностика «доехало ли обновление»).
  Дублирующий пинг версии делает сам `whisperkey.py` при старте (при живом
  `REMOTE_ASR_URL` шлёт `GET /health?v=<commit>`) — работает и со старым
  лаунчером; версия также показана в уведомлении «Готов к работе! (v<commit>)».
- **Доставка обновлений ужесточена (06.10.26).** Мягкий `pull --ff-only` при
  падении (локальная правка отслеживаемого файла, разъехавшаяся история)
  дополняется `fetch` + `reset --hard origin/main` — трогает только
  отслеживаемые файлы, `.env` переживает. Полный отказ теперь громкий:
  уведомление macOS «запущена старая версия» + строка в терминале; то же —
  при запуске из папки без `.git`. Заметка про чтение: `.command`
  обновляет сам себя — bash исполняет уже загруженную копию, поэтому
  в журнале моста строка `/health` без `?v=` сама по себе не доказывает
  старую сборку: решает пинг версии из питона.
- **Зачистка старой копии (06.10.26).** Перед `exec` лаунчер гасит процессы
  `python* whisperkey.py` (pgrep -f): висевшая от прошлого запуска копия
  слушала Option параллельно со свежей — два слушателя на одну клавишу
  дают перехват событий старой логикой (типичный след — «записал и сразу
  распознал» при живом тап-тап). Шаблон узкий, соседние программы не задевает.

Проверено на сервере до выката: живой POST FLAC в мост → 200 и полный текст
той же диктовки; стенд отказов пакета — 44 проверки/19 сценариев, включая
все три поведения ступени (быстрый путь, спасение, мёртвый мост).

**Reviver — догнать сторож, не дожидаясь тика (22.10.26).** Живой журнал:
обрыв домашнего интернета → remote-запрос падал с ConnectionError → Groq в
гео-блоке → запись уходила в локальную модель на 48-61с, хотя туннель каждый
раз успешно переподнимался за секунды. Теперь `whisperkey.py` ставит
`_engine.ctx.remote_reviver = _revive_bridge` (только Mac и только когда
сторож включён; `WHISPERKEY_NO_TUNNEL` отключает и его): при падении
remote-запроса или снятом адресе каскад сразу переподнимает туннель и
повторяет запрос ОДИН раз, сбросив `http_session` (мёртвый сокет старого
туннеля в пуле). Подъём под `_tunnel_lock` — сторож и reviver не плодят
два ssh. При реально лежащей сети после неудачного подъёма отдых
BRIDGE_REVIVE_REST_SEC=15с — туннелем занимается сторож. Стенд пакета:
4 новых сценария reviver (повтор-успех, reviver не поднял, адрес снят,
без reviver — прежнее поведение).

Той же ночью, второй живой инцидент флапа: запись 22.5с ушла в local на
34.8с, хотя туннель поднялся на ~20-й секунде локального декода. Причина —
спасательный повтор моста после local был мёртвым кодом: `remote_tried`
выставлялся до первой попытки в режиме remote, а спасательный блок требовал
`not remote_tried`. Теперь повтор по счётчику `remote_attempts < 2`
(тест `test_rescue_remote_retries_after_local` воспроизводит сценарий).
Плюс `_revive_bridge` проверяет живость туннеля ДО общей пробы интернета:
установленный ssh переживает краткий флап лучше свежего TCP-connect.

## Устройство (то, что осталось здесь)

Путь звука: микрофон (постоянный поток) → кольцо предзаписи → запись по клавише → каскад
распознавания (теперь — вызов `_engine.recognize`) → снятие водяных знаков → вставка.

**Каскад распознавания — три ступени, по очереди, не параллельно** (устройство — в
speech-engine/agent.md, здесь только что нужно знать локально):

1. **Deepgram nova-2** — первая попытка на каждой диктовке.
2. **Groq whisper-large-v3** со всей обвязкой (гейт плотности, стилевой проход,
   переносы) — когда Deepgram молчит, отключён, не настроен или отказал.
3. **Локальная модель** внутри второй ступени — когда интернета нет вовсе.

Замер 08.08.26 на калибровке Егора (текст, прочитанный вслух с листа — настоящий эталон,
не вывод другой машины, поэтому согласованные ошибки двух движков не притворяются
правильными словами) и на 20 записях спонтанной диктовки против эталона SaluteSpeech:

| | калибровка (808 слов) | спонтанная речь (1641 слово) |
|---|---|---|
| whisper (боевой конвейер) | 78.6% | 85.4% |
| **Deepgram nova-2** | **86.5%** | **88.6%** |

Deepgram победил на обоих материалах, и по времени тоже: 369 с аудио — 5.5 с против 8.9 с
у Groq; на пятиминутной записи 1.6 с против 5.6 с. Поэтому ступени идут именно по очереди,
а не параллельно с голосованием — вторая ступень не только не улучшает результат, она
и медленнее.

**Почему nova-2, а не nova-3 — УСТАРЕЛО с 22.10.26.** Августовский замер давал
80.9% против 86.1% через multilingual; свежий замер с `language=ru` дал обратное
(WER 9.1% < 10.6%), см. раздел «Deepgram nova-3 в диктовке» выше.

**Настройки — часть требования дословности, не вкусовщина.** `smart_format=false`:
включённый переписывает «двадцать пять» в «25» и стоит 2.8 пункта (83.3% против 86.1%
на замере) — а Егор просил «не форматируй». `filler_words=true`: «ну», «вот», «значит» —
часть его речи. `numerals=false` — по той же причине, что smart_format. `keywords`
проверены и отброшены: качества не дали (113 ошибок против 112 на калибровке), а первый
запрос с ними растягивается до 4.5 с. Не меняй эти четыре параметра без повторного замера
на `_eval/calib/dg_tune.py` — там же лежит скрипт, которым они подбирались.

**Отказы Deepgram разделены по лечимости.** 401/402/403 (ключ, деньги, доступ) — не лечится
повтором, движок отключается на `DEEPGRAM_BLOCK_SECONDS` (15 минут) и сообщает об этом
через `notify`, чтобы человек знал, что работает на второй ступени, а не терял качество
молча. 429/5xx — короткий повтор, `DEEPGRAM_RETRIES`. Пустой транскрипт и нераспознанный
JSON — не ошибка, а сигнал уйти на whisper: диктовка не должна теряться из-за формы ответа.

`meta.json` теперь пишет `engine` ("deepgram" | "whisper") — без этого поля нельзя было бы
отличить, ступень какого движка дала конкретный результат, когда придёт следующая жалоба
на качество.

## Локальное хранилище записей (20.10.26)

Каждая диктовка дублируется в `~/Library/Application Support/WhisperKey/Recordings` рядом
с корпусом `WhisperKey-Eval-Samples`.

- **Папка локальная, не в iCloud** (`~/Library/Application Support`).
- **Путь настраивается:** переменная `WHISPERKEY_RECORDINGS_DIR` в `.env`; если не задана —
  используется путь по умолчанию.
- **Сохраняются только реальные записи:** длительностью не менее `RECORDINGS_MIN_DURATION`
  (0.5 с), короткие случайные касания игнорируются.
- **Формат:** WAV 16 кГц 16 бит моно, имя `YYYYMMDD_HHMMSS_<duration>s_id<session>.wav`.
- **Жизнь 24 часа:** почасовая очистка через launchd-агент, который удаляет файлы
  старше 1440 минут и пишет журнал в `~/Library/Logs/whisperkey-cleanup.log`. Агент
  устанавливается отдельной командой из `tools/whisperkey-recording-cleanup.sh` — он
  не активен по умолчанию и не удаляет ничего, пока вы его не включите.
- **Независимость от корпуса оценки качества:** корпус `WhisperKey-Eval-Samples` продолжает
  работать как раньше; хранилище записей — отдельный механизм, не заменяющий корпус.
- **Тесты:** `tests/test_recordings.py` — сохранение, переопределение папки, пропуск коротких
  записей, удаление только состаренных файлов, неприкосновенность свежих и файлов снаружи.

## Плашка внизу экрана — копия Wispr Flow (28.09.26, только mac)

`pill.py`. Полоска 40×8 над Dock — программа ждёт; капсула 73×30 с белой волной — пишет;
98×30 со спиннером — распознаёт; 91×30 с красной обводкой на 1.5 с — ошибка/пусто. Все
размеры, цвета, кривые и формула волны вынуты из самого Wispr Flow 1.6.872 (стили окна
`status` в `~/wispr-flow/app/app.asar`, положение «снизу»), не на глаз; сверка — рендер
оригинальных стилей в Chromium рядом с `tests/pill_preview.py`, совпало по всем 5 состояниям.

Неочевидное:
- **Главный поток теперь крутит цикл событий AppKit** (`pill.run_forever`), клавиатура — в
  своём потоке pynput, как и была. Окна macOS живут только в главном потоке, поэтому из
  других потоков — лишь `model.set_state/set_level_rms` (под замком) + `AppHelper.callAfter`.
- **Плашка не имеет права уронить диктовку.** Нет AppKit / окно не поднялось → `NullPill` и
  старый путь `listener.join()`; сбой рисования в работе → плашка прячется до перезапуска.
  `WHISPERKEY_PILL=0` в `.env` — выключить совсем, всё как раньше баннерами.
- При живой плашке баннеры «Запись / Распознаю / Текст готов» молчат; баннеры о проблемах
  (потеряно, локальная модель, пусто, сбой, микрофон) остаются — в них текст.
- **Чувствительность волны откалибрована под микрофон Егора (04.10.26), не по Wispr.**
  Замер 40 диктовок корпуса: речь −38…−15 дБ, медиана −22 дБ. В Wispr-формулу уровня

  затем 7→8.4 (+20% амплитуды по просьбе Егора 05.10.26 — «точки видно, но мало»).

  (макс. столбик ~25 px при 30 px).
- Смена состояния в `process_audio` — под `state_lock` вместе с фазой, иначе новое нажатие
  между двумя строками получало «запись», а старая диктовка тут же затирала её в «покой».

## «Залипание» двойным касанием — как у Wispr Flow (05.10.26)

Тап-тап по правому Option включает запись без удержания: диктовка идёт, руки
свободны, плашка и волна живут как обычно; следующее нажатие завершает — как
одиночное касание у Wispr. Обычный «нажал-держи-говори» не изменился.

Механика (обработчики `on_press`/`on_release` в `whisperkey.py`):
- Окно двойного касания — от ОТПУСКАНИЯ короткого тапа: первое нажатие
  <`LATCH_TAP_MAX_SEC` (1.3 с; живой тап Егора мерится ~0.72 с — запас нужен)
  считается «тапом», и после отпускания открывается `LATCH_WINDOW_SEC` (0.7 с)
  на второе касание (в справке Wispr — «within half a second»; счёт именно от
  старта записи на деле резал спокойный темп, потому окно привязано к
  отпусканию).
  Клавишу держали дольше порога — это «нажал-держи-говори»: стоп мгновенный
  по отпусканию, без всякой задержки и без окна. Пришедшее в окне касание
  подхватывает тот же захват — без разрыва звука и без мигания плашки;
  не пришедшее — обычный финализ через `_begin_stop()` (бывшее тело
  on_release, логика без изменений).
- `on_press` в этом окне (фаза ещё `recording`, до конца дедлайна есть время)
  поднимает `latch_active`: отпускания дальше игнорируются, запись жива.
  Проверка идёт ДО дебаунса — иначе быстрый тап-тап съедается
  `TRIGGER_DEBOUNCE_SEC` (0.35 с) целиком. Фильтра «минимальный зазор между
  касаниями» нет НАМЕРЕННО (урок 05.10.26, журнал мака): macOS отдаёт
  модификаторы обработчику пачкой, второе нажатие Егора приходило через 1 мс
  после события отпускания при реальном зазоре — порог в миллисекундах
  доставки отсекал настоящие касания.
- Нажатие при `latch_active` завершает запись сразу по нажатию (не ждёт
  отпускания — отзывчивее, как у Wispr) тем же `_begin_stop()` — НО если оно
  пришло в первые `LATCH_CANCEL_SEC` (0.5 с) после залипания, это у Wispr
  отмена: `_cancel_recording()` глушит запись без распознавания и вставки.
- `LATCH_MAX_SEC` (900 с) — потолок залипшей записи, сторож `_latch_watchdog`:
  страховка от «забыл включённой на ночь» — буфер не раздувается бесконечно.
- Поколение `_release_seq` отменяет просроченные финализ-потоки; гонку «второе
  касание ровно на границе окна» решает `state_lock` — выигрывает первый вошедший.
- **Потерянное отпускание лечится само (06.10.26).** Нажатие при «ещё нажатой»
  клавише невозможно физически — значит, событие отпускания не дошло (macOS
  может сливать быстрые переключения модификатора). `on_press` в этом случае
  считает отпускание случившимся прямо перед нажатием: открывает окно и дальше
  общий путь второго касания. Без этого путь с потерянным release давал в
  точности жалобу «так и не залипает — записал и сразу распознал».
- Диагностика темпа: каждое событие семейства Option (левый/правый/alt_gr, vk
  58/61/62) пишется в `~/.whisperkey_taps.log` с миллисекундами и решением
  программы (`→ LATCH`, `→ касание мимо окна`, `→ пропуск, фаза …`); при старте —
  метка `=== запуск, сборка <commit> ===`. Отдельно версия сборки уходит в
  health-запрос моста (`/health?v=<commit>`) — в журнале voice-bridge видно,
  какая сборка реально запущена на Mac.

Проверено симулятором событий на сборке модуля из исходника (та же техника, что
у стенда отказов): 33 проверки — короткий стоп в окне, мгновенный стоп длинного
удержания, залипание с жизнью записи после отпускания, завершающее нажатие,
отмена третьим касанием, медленный второй тап без залипания, ленивый тап-тап
~1 с с залипанием, залипание при потерянном release и при потерянном press
(второе окно открывает сам release).
- Модель кадра — чистая математика, проверяется без Mac: `tests/test_pill.py`, картинки —
  `tests/pill_preview.py` (нужен Pillow, только для просмотра). Сам AppKit-слой на сервере
  не запускается — проверяется глазами на Mac.
- Windows (`whisperkey_win.py`) плашки пока нет: там нужен свой слой (tkinter/Win32), модель
  `PillModel` переиспользуется как есть.

## Граница между mac и Windows

Копируется дословно: текстовые фильтры, промпт, разбор ответа модели, гейт плотности,
нарезка и склейка, троттлинг и повторы, упаковка WAV, вся логика деградаций. Если правишь
это в одном файле — механически переноси во второй, расхождений тут быть не должно.

Расходиться можно ровно в семи местах, и в win-файле они помечены «платформенная точка N»:

1. **Однократный запуск** — именованный мьютекс `Local\WhisperKey` вместо `fcntl.flock`.
   pid-файл, стоявший здесь раньше, не даёт ни атомарности, ни освобождения при kill,
   а Windows переиспользует PID: чужой процесс с тем же номером намертво блокировал старт.
2. **Уведомления** — `print` из daemon-потока плюс `winsound.MessageBeep`, без баннера.
   Асинхронность обязательна: `notify` зовётся под `state_lock` и внутри колбэка хука,
   а замерший stdout (QuickEdit) или `UnicodeEncodeError` оттуда убивают listener pynput.
   PowerShell-тост запрещён: 300–800 мс и мигание окном в горячем пути клавиши.
3. **Вставка** — буфер обмена плюс `SendInput` своим ctypes-вызовом. `kb.press('v')` под
   Windows уходит как `KEYEVENTF_UNICODE` с `wVk=0` и акселератором не становится (это
   происходит на русской раскладке, где `VkKeyScan('v')` возвращает −1); нужен явный
   `vk 0x56`. **Возврат `SendInput` блокировку UIPI не видит** — документация Microsoft:
   «neither GetLastError nor the return value will indicate the failure». Поэтому окно
   от администратора проверяется отдельно, `_foreground_input_blocked`: `OpenProcess`
   с `PROCESS_QUERY_LIMITED_INFORMATION` на процессе активного окна, отказ 5 = наш ввод
   туда не дойдёт. Буфер восстанавливается, только если вставка не заблокирована; во всех
   остальных случаях текст остаётся в буфере, и пользователю об этом говорят.
4. **Рабочий стол** — через реестр (`Shell Folders\Desktop`), не `~/Desktop`: при OneDrive
   с перенаправлением папок последний не существует, и запись по нему создаёт невидимый каталог.
5. **Приоритет** — `ABOVE_NORMAL_PRIORITY_CLASS`. `p.nice(-10)` из mac на Windows бросает
   исключение (там ждут класс приоритета, а не число) и молча ничего не делает; `HIGH` выше
   активного окна и даёт лаг ввода. `cpu_affinity` на Windows работает — и потому запрещён:
   конкурирует с аудио-колбэком PortAudio.
6. **Кодировка stdout** — `reconfigure(utf-8, errors='replace')` и подмена `None`-стримов
   до первого print, плюс `chcp 65001` в `run_whisperkey.bat`. Это не косметика: печать идёт
   из колбэка хука, и одно исключение там останавливает клавишу до перезапуска.
7. **Клавиша** — `vk 165` (VK_RMENU). Код 61 (mac-артефакт) удалён. Три вещи, каждая из
   которых по отдельности выключает диктовку целиком:
   * **pynput отдаёт правый Alt как `Key.alt_gr`, а не `Key.alt_r`.** В `_win32.py` обе
     константы объявлены с одним `vk 165` (у `alt_r` флаг EXTENDEDKEY, у `alt_gr` нет),
     из-за разных флагов enum их не схлопывает, а таблица listener'а строится словарём
     `{key.value.vk: key}` — и `alt_gr`, объявленный позже, затирает `alt_r`. Сравнение
     `key == Key.alt_r` даёт False. Запасная проверка `key.vk` тоже не работает: у члена
     enum своего `.vk` нет, он в `.value`. Отсюда `_key_vk` и три пути в `is_trigger`.
   * **Открытие микрофона нельзя делать в `on_press`.** pynput ставит `WH_KEYBOARD_LL`
     и качает очередь сообщений одним потоком: пока `on_press` работает, хук позвать
     нельзя, а на превышении `LowLevelHooksTimeout` (300 мс) Windows 7+ снимает хук молча.
     Открытие устройства под MME стоит сотни миллисекунд, с повторами — до полутора секунд.
     Поэтому `_start_capture_async`; уведомление «Запись…» уехало туда же, чтобы «говори»
     по-прежнему не опережало первый сэмпл.
   * Одиночный Alt открывает меню активного окна, после чего Ctrl+V уходит в меню, —
     поэтому сразу после старта записи, пока Alt удерживается, инжектится «маскирующее»
     нажатие `vk 0xE8`.

Плюс две вещи, у которых на macOS нет аналога и в эталоне их взять неоткуда: отказ микрофона
по системному запрету («Конфиденциальность → Микрофон») выглядит как ТИШИНА, а не как ошибка —
ловится проверкой пика амплитуды; и `pyperclip.copy` падает, когда буфер держит менеджер буфера
или проброс в RDP, — поэтому копирование идёт с повторами, а пустой прежний буфер не
восстанавливается вовсе (для файлов и картинок `paste()` отдаёт `''`).

Предзапись на Windows выключена так же, как на mac, но по другой причине: там её убил CoreAudio
(-10863), здесь она просто не проверена на живой машине. Включать `PREROLL_ENABLED = True`
имеет смысл — под MME открытие устройства дороже, чем на Mac, и делается оно прямо в колбэке
хука, — но только с проверкой руками по логу («предзапись 500 мс», а не «предзапись пуста»).

## Что здесь неочевидно

**Промпта нет, и это решение по замеру.** `ASR_CONTEXT_PROMPT = ""`.

Сначала он был тематическим («Русская деловая речь. IT, программирование…») — такой протекает
в текст там, где речь не разобрана: замерено «Субтитры делал DimaTorzok» вместо 74 слов живой речи.
Потом его заменили на образец одной пунктуации («Да, конечно. Хорошо. А что дальше?») — на
45-секундных окнах разговора это давало 1033 слова и 105 точек против 975/97 у тематического.

**Перенос этого вывода на короткую диктовку был ошибкой.** Замер 06.08.26 на 8-секундных клипах,
6 окон: 80 слов с промптом против 112 без него — минус 29%, причём одна фраза целиком схлопнулась
в «Да.», то есть в слово из самого промпта. Проверка по длительности дала не зависимость,
а разброс: 8 с −29%, 15 с +9%, 25 с −8%, 40 с +21%. Промпт — лотерея, и на коротком входе
проигрыш означает потерю всей фразы. Для диктовки это неприемлемо.

Проверялись и «безопасные» варианты — чем нейтральнее промпт, тем хуже: абстрактный дал 73 слова
и 2 пустых ответа из 6, описательный 54 слова и 3 пустых, из одних знаков препинания — 10 слов
и 4 пустых. **Не возвращай промпт без замера на коротких клипах.**

Единственное, что промпт давал полезного, — заглавная буква в начале (6 из 6 против 1 из 6).
Она теперь ставится локально флагом `CAPITALIZE_FIRST`: слова при этом не меняются, потерять
фразу невозможно. Точка в конце остаётся выключенной (`FORCE_TRAILING_DOT`) — диктовка часто
идёт в середину предложения, и навязанная точка ломает мысль.

**Знаки препинания берутся вторым проходом, а не промптом.** `STYLE_PROMPT`,
`PUNCT_TRANSFER_MIN_SECONDS`, `transfer_punctuation`.

Убрав промпт, мы вернули слова и потеряли читаемость: без него почти четверть диктовок приходит
«простынёй» — участком от 20 слов подряд без единого знака. Замер 06.08.26 на 101 реальной
диктовке Егора (38 минут речи, весь корпус `WhisperKey-Eval-Samples`):

| вариант | слов | знаков на 100 слов | простыней |
|---|---|---|---|
| промпт в основном запросе (как было) | 3880 | 39.6 | 8 |
| без промпта | 4076 | 31.5 | 23 |
| два прохода со слиянием | 4076 | 39.6 | 5 |

Подбором одного промпта это не решается, проверено: мета-инструкция («расставь знаки») срезала
160-секундную диктовку с 229 слов до 45 и 35-секундную с 58 до 10; слова-заполнители теряли до
трети на других записях. Промпт не умеет добавить знаков, не получив права подставлять свои слова.

Отдельная модель для пунктуации тоже отпала: llama-3.3-70b переписывала слова в половине кусков
(«вообще» → «generally», удаляла слова, «исправляла» грамматику), проверку сохранности проходило
69 % кусков при задержке 6.5 с. Знаки по паузам из `words[]` не работают вовсе — Егор диктует
без разрывов, на 101 записи алгоритм добавил 0.3 знака на 100 слов.

Как устроено сейчас: при длительности от `PUNCT_TRANSFER_MIN_SECONDS` (12 с) до
`PUNCT_TRANSFER_MAX_SECONDS` (600 с) **одновременно** с основным запросом уходит второй, со
`STYLE_PROMPT`. Слова берутся только из прохода без промпта; `transfer_punctuation` находит
совпадающие участки через `difflib` и переносит с них знаки и заглавные. Слово из промпта попасть
в результат не может — оно не совпадёт и будет отброшено. Инвариант проверяется прямо в функции:
если список слов на выходе не равен входному, возвращается исходный текст.

Почему параллельно: второй запрос не добавляет ожидания. Ждём его не дольше 8 секунд — текст
важнее оформления, задерживать вставку из-за знаков нельзя.

Цена: два запроса вместо одного на записях длиннее 12 секунд. Квота Groq — 7200 аудио-секунд
в час, при обычном сценарии это не жмёт. Порог снизу не случайный: на 47 записях короче 15 секунд
простыня была ровно одна, второй запрос там был бы расходом без выигрыша.

**Открытая проблема, которой мы не занимались: английские термины.** Модель с `language=ru`
пишет их кириллицей по звучанию: «код код» вместо Claude Code, «вы спроси» вместо WhisperKey,
«ноутбука л.м» вместо Notebook LM. В корпусе 16 вхождений одного только «код», причём часть
из них — настоящее русское слово («сам код тупит», «VS код»), поэтому простой заменой это не
лечится. Нужен словарь из многословных сочетаний, подтверждённый Егором. `BRAND_NAMES` сейчас
чинит только те названия, что уже пришли латиницей.

**Звук уходит в облако ускоренным на 3%.** `ASR_TEMPO = 1.03`, `_change_tempo`, `_restore_timeline`.

Замер 06.08.26 на 19 диктовках Егора против эталона SaluteSpeech (1632 слова эталона,
метрика — только слова, знаки и регистр сняты):

| темп | ошибка |
|---|---|
| 1.00 (как было) | 14.8% |
| **1.03** | **13.3%** — лучше на 10 записях, хуже на 3 |
| 0.97 | 13.9% — лучше на 7, хуже на 6 |
| +0.7 с тишины в начало | 16.5% |

Бутстрап 20 000 пересборок для 1.03: −1.50 п.п., ДИ95 [−3.36; +0.34], хуже базы
в 5% пересборок. **Строго это не доказано** — интервал краем задевает ноль, а на
19 записях различимо только ±2 пункта (см. раздел про надёжность эталона).
Правка принята потому, что ничем не рискует: слова не трогаются, задержка не растёт,
возврат к прежнему поведению — одна константа.

Почему работает: у whisper окно 30 секунд и жёсткая привязка к темпу речи, сдвиг
темпа меняет весь путь декодирования. Частота дискретизации в заголовке WAV при этом
НЕ меняется — именно поэтому для модели речь звучит быстрее. Подмена частоты вернула
бы исходное звучание и обнулила эффект; на это есть тест.

Область действия: только облачный проход. `create_audio_wav` вызывается лишь из
`transcribe_cloud_turbo`, поэтому локальная модель получает исходный звук. Корпус
эталонов (`_write_raw_recording_wav`) тоже пишет исходный — иначе следующий замер
делался бы по уже обработанному материалу; на это есть отдельный тест.

`_restore_timeline` умножает `start`/`end` в `segments[]` и `words[]` обратно на
`ASR_TEMPO` сразу после ответа. Без этого гейт плотности, подстановка из `words[]`
и снятие перекрытий при склейке длинных записей считали бы по сжатой шкале.

**Что НЕ работает и повторять не надо** (замерено там же): добавление тишины в начало
(16.5%); замедление темпа (выигрыш не отличим от нуля).

**Хвост записи и пропуски микрофона.** `TAIL_CAPTURE_SECONDS`, `audio_dropouts`.

Егор сообщил 07.08.26: последнее слово регулярно не попадает в текст, хотя клавишу
он отпускает заметно позже. Захват хвоста поднят с 0.6 до 1.0 секунды. Прежние
0.6 ставились ради скорости, но диктовка уходит в облако на 2–4 секунды, и лишние
0.4 с на этом фоне незаметны, а потерянное слово заметно всегда.

**Замером это подтвердить нельзя, и вот почему.** Корпус эталонов содержит уже
записанный звук: то, что не попало в `.wav`, отсутствует в нём одинаково и у нас,
и у Сбера. Сравнение двух расшифровок ОДНОГО файла видит только ошибки
распознавания, но слепо к потерям захвата. Проверяется это лишь на калибровочном
тексте, где известно, что было произнесено — `_eval/calib/`.

Проверено и НЕ помогает: 0.5 с тишины в конец записи перед отправкой — 15.3%
против 15.3% без неё (одна ошибка на 1632 слова, шум).

`audio_dropouts` считает переполнения входного буфера PortAudio за время записи
и выводит их в уведомление отдельной строкой. Это единственный класс потерь,
который распознавание не лечит: сэмплы выброшены железом, звука уже нет. Раньше
такое уходило только в терминал, и пропавшие слова списывались на модель.

**Отдельно: возврат слов из `words[]` невозможен, не пробуй.** Гипотеза выглядела
разумной — половина потерянных относительно эталона слов «есть» в `words[]`.
Проверка показала, что это артефакт подсчёта: проверялось наличие слова ГДЕ УГОДНО
в списке, а «и», «я», «вот», «в» встречаются там десятками. Позиционное сравнение
даёт ровно 0 слов, которые есть в `words[]` и отсутствуют в собранном тексте:
1620 слов в тексте против 1617 в `words[]`. Гибридная сборка уже вытащила всё.

Почему нельзя просто поставить словарь в основной запрос: промпт заставляет модель

В `TERM_CANON` не должно быть обычных русских слов. «код», «дизайн», «агент»,
«промпт», «токен» — живые слова языка, и подстановка на них испортила бы речь.

Claude и «бокал» вместо Notebook: это существующие слова, отличить их от ослышки
без словарного прохода нельзя — а с ним они и так приходят правильными.

словоформ, которую Егор запретил («как услышал, так и пиши, пусть криво»;
жалоба на перефразированные окончания). Замер 08.08.26 давал +9/-1 на
командах, но приоритет дословности выше. Функция в `transfer.py` осталась,
вызовы сняты в `speech_engine/dictation.py` и `whisperkey_win.py`.

`transfer_endings`, `ENDING_MIN_STEM`,
образцы императивов внутри `STYLE_PROMPT` (не применяется с 28.10.26).

Самый частый класс ошибок у Егора: он диктует команды, а модель ставит форму по
привычке субтитровых корпусов — «сохрани» → «сохраняет», «выстрой» → «выстроить»,
«реализуй» → «реализует», «раздели» → «разделить». Звук при этом услышан верно:
основа слова всегда совпадает, расходится только хвост.

их вклад на живой речи, надо складывать в мету и промежуточный текст — не сделано.

**Вставка идёт с подтверждением буфера, а не по таймеру.** `_put_clipboard`,
`_restore_clipboard_async`, `CLIPBOARD_WAIT_SEC`, `CLIPBOARD_RESTORE_SEC`.

Егор сообщил 08.08.26: иногда вместо продиктованного текста вставляется прежнее
содержимое буфера обмена. Причин было две, обе — гонки во времени.

1. **Вставка обгоняла запись в буфер.** Код клал текст через `pbcopy`, спал
   фиксированные 0.1 с и жал Cmd+V, ни разу не проверив, что буфер обновился.
   Не успела система — вставляется прежнее. Теперь `_put_clipboard` опрашивает
   `pbpaste`, пока там не окажется именно наш текст (до `CLIPBOARD_WAIT_SEC`),
   и **при отсутствии подтверждения вставка не делается вовсе** — вставить
   в этот момент значило бы отдать человеку его старый буфер вместо диктовки.
   Текст при этом набирается напрямую через `kb.type`.

2. **Возврат прежнего буфера обгонял вставку.** Старое содержимое возвращалось
   через 0.5 с. Медленные приложения (браузер, Slack, Notion) читают буфер
   позже — и забирали уже возвращённый старый текст. Пауза поднята до
   `CLIPBOARD_RESTORE_SEC` = 2.5 с, и перед возвратом проверяется, что в буфере
   всё ещё НАШ текст: если человек успел скопировать своё, его копия важнее.

Оба правила закрыты тестами в стенде отказов. Тесты платформенные: в win-версии
вставка идёт через Windows API, и там они пропускаются.

## Красные зоны

**`BOH_TAIL_MARKERS` — только водяные знаки, не слова языка.** Там были «корректор» и «продолжение
следует»; фраза «Он корректор и дизайнер» превращалась в «Он.» — потеря 75%. Прежде чем добавить
строку в этот список, спроси себя, может ли человек сказать это всерьёз.

**Ничто не должно молча исчезать.** Кусок, который не распознался, оставляет в тексте метку
`[не распознано MM:SS]`, уход на локальную модель и снятый водяной знак попадают в уведомление.
Прежняя версия при падении одного куска из четырёх вставляла пустоту и не показывала ни одного
уведомления — три успешно распознанных куска просто выбрасывались.

**Исключение — доказуемо пустая диктовка (05.10.26).** Случайное касание и тишина обязаны
исчезать молча, без текста и баннера (как у Wispr): человек ничего не говорил — показывать
«не расслышал» нечего. Три слоя, каждый молчит только там, где вставлять объективно нечего:
(1) `<10` фреймов (≈0.3 с) — молча; исключение — **0 фреймов**, это мёртвый микрофон, баннер
«Слишком короткая запись» остаётся как признак поломки; (2) `SILENCE_GATE_DB = -45` — пик RMS
по фреймам 512 ниже порога (поле между полом комнаты ~-50 дБ и самой тихой речью в корпусе
-38 дБ) — молча до ASR, запросы не тратятся; пик, не среднее: речь всплесками, щелчок клавиши
— один сэмпл — гейт не открывает; (3) `watermarks.boilerplate_only` — весь результат целиком
субтитровая заглушка Whisper («Продолжение следует…», «спасибо за просмотр», скобочные
пометки звука) — молча после ASR. Проверка строго на весь текст: «задача сложная, но
продолжение следует» — живая фраза и остаётся. Пустой ответ движков на записи со звуком —
по-прежнему баннер «Речь не распознана»: это отказ, не пустота.

**Регулярки по тексту — источник тихой порчи.** Правило «пробел после точки» ломало числа, версии
и имена файлов («3.5» → «3. 5»). Любое новое правило обязано пройти `tests/test_verbatim.py`.

**`global` во вложенной функции не наследуется.** В `delayed_stop` (внутри `on_release`)
объявления из `on_release` не действуют: `session_phase = "idle"` писалось в локальную
переменную, модульная фаза навсегда оставалась `"processing"`, и `on_press` дальше выходил
по первой же проверке. То есть одно случайное короткое касание клавиши намертво выключало
диктовку до перезапуска. Правилось в обоих файлах одинаково. Любая машина состояний здесь
живёт на модульных переменных — при добавлении вложенной функции перечисляй в `global` ВСЁ,
что она присваивает, включая то, что уже объявлено этажом выше.

его отдельно, гоняя `on_press`/`on_release` на заглушенном `start_audio_stream` и глядя
на `session_phase` после короткого нажатия и после отказа микрофона.

Что тесты закрыть не могут и проверяется только руками на Mac: реальный захват с микрофона,
вставка в активное окно, права универсального доступа, величина срезания начала фразы.

## Правка 19.10.26 — вставка с проверкой факта, работа без VPN, страховка чистки

Три жалобы Егора: текст иногда не вставляется при «[insert success]»; диктовка

**Вставка — лестница транспортов (редизайн вечером 19.10.26).** Причина
второго прохода: при нечитаемом поле (Brave) первый вариант слал Cmd+V и
следом «добивку» меню — ДВА слепых удара в цикле → живые дубли текста.

Лестница `direct_insert` (возвращает секунды для строки `[timing]`):

**Быстрый слой pyobjc (вечер 19.10.26, вторая жалоба «после плашки жду
~секунду»).** Каждый вызов osascript — порождение процесса ~0.1–0.3с, и на
нечитаемом поле их шло 3–4 подряд — это была почти вся видимая секунда.
AppKit/Quartz уже приезжают с pynput, поэтому основные транспорты идут
прямыми вызовами API внутри процесса (миллисекунды); любой отказ быстрого
пути → прежний osascript-путь теми же статусами, поведение не меняется:
`_ax_smart_insert` → сначала `_ax_smart_insert_fast` (AX-запись
AXUIElementCopy/SetAttributeValue + NSWorkspace для имени/pid frontmost);
`_blind_strike` → сначала `_blind_strike_fast` (`_menu_paste_press` —
AXPress на ЖИВОМ пункте «Paste/Вставить», AXEnabled=False пропускается,
иначе клик по мёртвому вернул бы «успех» без вставки → тихая потеря;
далее `_cgevent_paste` — Cmd+V синтезированным событием Quartz в pid или
во frontmost); `_clipboard_now`/`_put_clipboard` — NSPasteboard вместо
pbcopy/pbpaste. Импорты pyobjc под try — нет пакета → старый путь целиком.
`_send_paste_via_menu` (терминал/Secure Input в читаемой ветке) — сначала
тот же `_menu_paste_press(pid)` (не зависит от имени процесса и от права
«управлять System Events»), osascript — запасной; при отказе меню — ещё
один `_send_paste_keystroke` прежде чем сдаться на посимвольный ввод.
Внимание локализации: на русской macOS Terminal.app называется «Терминал»
— `_TERMINALS` обязан содержать кириллическое имя, иначе ветка «ложный
AX-успех в экран вывода» не включается и текст теряется молча (27.10.26).

1. `_ax_smart_insert` — быстрый pyobjc-вызов или ОДИН osascript на всё:
   frontmost + фокусный элемент + при надобности выставка
   `AXEnhancedUserInterface` на процессе
   (Chromium/Electron отдают текстовые поля в AX-дерево только после неё —
   это лечит «нечитаемое веб-поле» без всякого действия пользователя) +
   сплайс по `AXSelectedTextRange` + запись `AXValue` + чтение назад.
   Статусы: WROTE (verify в Python через `_insert_verified`), WRITEFAIL
   (читаемо, запись отказана → буферный путь с реальными вердиктами),
   UNREADABLE / NOFOCUS / ERROR. Буфер обмена и клавиши не трогаются.
   Цель выбирается в момент вставки (frontmost/focused), не на момент начала
   записи: приложение не активируется обратно, пользователь переключается
   свободно во время диктовки.
2. UNREADABLE/NOFOCUS + браузер → `_js_insert`: AppleScript-JS
   активной вкладки `execCommand('insertText')` + чтение
   `document.activeElement` назад — настоящая проверка там, где AX молчит.
   Требует «Allow JavaScript from Apple Events» в браузере (Вид →
   Разработчик); выключен — один баннер с инструкцией один раз
   (`_js_flag_notified`), приложение кэшируется в `_js_off` и JS больше
   не пробуется в этой сессии. Текст в JS едет base64.
   (Проба записи в AXSelectedText из горячего пути убрана по жалобе
   «долго жду вставки» — функция `_ax_selected_text_insert` осталась,
   вернуть при надобности — один вызов в direct_insert.)
3. Буферный путь (только если ступени 1–2 не сработали; буфер пишется
   только здесь): читаемое поле — один Cmd+V с опросом `_poll_insert`;
   меню разрешено только если Cmd+V доказанно не был отправлен. После любого
   отправленного транспорта повторов нет. Пустое поле при read-back может
   означать, что пользователь уже нажал Enter: повторная вставка тогда снова
   выводила отправленный текст в поле Claude UI (живой случай 20.10.26).
   Поэтому `WROTE`, отправленный Cmd+V, меню или JS закрывают диктовку даже
   без verify. НЕчитаемое поле — РОВНО ОДИН слепой удар вызовом
   `_blind_strike` (меню «Вставить» → точечный Cmd+V → во frontmost — внутри
   процесса или одним osascript). Проба на ЖИВОМ пункте меню — уже сам удар:
   AXPress/click может отчитаться ошибкой ПОСЛЕ реальной вставки, поэтому
   добивка запрещена. Тот же класс закрыт в `_js_insert`: при
   `execCommand=false` поле всё равно перечитывается.
   Опроса нет —
   честный `[insert sent]`. Разблокировка AXEnhancedUserInterface
   кэшируется по приложению в `_ax_unlock_failed` — после первой
   неудачной попытки не повторяется (~0.1с экономии на каждой диктовке).
4. Доказанный отказ/неотправка всех → `kb.type` посимвольно. При
   sent=True по слепому удару НЕ набираем — тот уже мог встать, набор
   был бы вторым текстом. Всё отказало → `[insert FAILED]` + звук Basso
   + notify, текст остаётся в буфере.

Option зажат (Cmd+Opt+V = «со стилем») → буферный путь пропускается,
сразу набор; физическое состояние Option — Quartz CGEventSourceFlagsState
(флаг listener'а залипает при потерянном release). AX- и JS-ступеням
Option не мешает, поэтому ожидание отпускания стоит только перед
буферным путём — в хорошем пути его нет вообще.

Формат финальных строк: `[insert success|sent|FAILED] '…' (via, X.XXс)` —
via: ax-write / axsel / js / paste / menu / key / type. Плюс в
process_audio строка `[timing] asr=X.XXс insert=Y.YYс всего=Z.ZZс` —
«стало дольше» всегда жило на стороне вставки, разделяем замеры.
